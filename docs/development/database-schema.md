# Generated database schema v1

`generated/kanji_db.json` is generated by `tools/build_database.py`. Do not edit it.
The UTF-8 JSON envelope contains `schema_version: 1`, `generated: true`, `sources`,
and `entries`. `sources` records archive basenames and SHA-256 hashes; KANJIDIC2
also records its XML header. The KanjiVG release date is identified by its archive
filename, not an invented internal version. No timestamps or absolute paths enter
the output. Objects sort by key, arrays retain upstream order, JSON is compact
with one terminal LF. Identical source bytes produce identical output bytes.

The default source location is `data_sources/` for both archives, with no root
fallback. `sources.*.file` intentionally remains a basename, not a filesystem path;
moving identical input bytes does not change provenance identity or database bytes.
`schema_version` versions the consumer-facing representation, independently of
upstream release versions. Consumers must reject unsupported versions rather than guessing.

`entries` is keyed by every KANJIDIC2 literal, including supplementary Unicode
scalars. The literal is not duplicated in dictionary records. Each record has:

| Property | Meaning |
| --- | --- |
| `meanings` | Full English meaning array in source order; empty if unavailable |
| `readings.on`, `readings.kun` | Authoritative Japanese readings; punctuation, kana and hyphens unchanged; empty arrays allowed |
| `strokes` | First KANJIDIC2 stroke count, if supplied; subsequent counts are documented upstream as common miscounts |
| `frequency` | Positive upstream rank, omitted when unavailable |
| `structure` | KanjiVG group tree, omitted when no canonical glyph matches |

Non-English meanings, nanori, SKIP, grades, non-Japanese readings and other
dictionary indices are not retained. Multiple reading/meaning groups, if supplied
in future, are concatenated in source order and reported in statistics; association
between those groups is not represented in v1. The supplied source has none.

Structural nodes retain the following optional fields:

| Property | Type / interpretation |
| --- | --- |
| `char` | Verbatim `kvg:element`, which may be a character, CDP identifier or descriptive string |
| `base` | Verbatim explicit `kvg:original`; absence means use `char` |
| `position` | Verbatim upstream position, including `nyo`, `nyoc`, `tare`, `kamae` and unusual IDS-like labels |
| `radical` | Verbatim convention: observed `general`, `tradit`, `nelson`, `jis`; never a boolean |
| `phon` | Verbatim phonetic annotation; not necessarily a dictionary key |
| `children` | Ordered group nodes; omitted for leaves |
| `variant`, `partial`, `tradForm`, `radicalForm` | Boolean annotations when present |
| `part`, `number` | Upstream string identifiers for split/repeated components |

Unnamed groups (including empty objects) are retained: they group strokes without
claiming a character identity. Split components are not independent complete
characters. Keeping flags and part identifiers prevents the renderer from making
that assumption. Child groups are not necessarily an exhaustive partition into
named components: strokes directly under a group are intentionally not stored.
Geometry, stroke numbers, SVG IDs and styling are excluded.

Component meaning lookup is normalized, not duplicated on each node:

```python
key = node.get('base', node.get('char'))
meanings = database['entries'].get(key, {}).get('meanings', [])
```

`component_meanings()` implements this operation for tooling/tests. This preserves
the entire authoritative meaning array in the database once. No global variant
table, transitive mapping or fallback from an unresolved explicit base is used:
original mappings are local to each occurrence. The future payload generator must
resolve references before sending self-contained data to a card. Structural root
`char` remains present for a uniform tree representation; root meanings and direct
components are not stored a second time.

Radicals may occur at any depth, including the root. A consumer must traverse the
tree. Prefer `general` for ordinary presentation; preserve other conventions.
No radical is inferred from dictionary metadata when structure is unavailable.

Only canonical hexadecimal SVG filenames are selected. Suffixed variants are
reported and excluded rather than arbitrarily replacing a default glyph. Missing
or mismatched roots, duplicates, malformed XML and unknown structural attributes
fail the build. ElementTree reads the supplied inline DTD namespace defaults but
does not fetch the SVG external DTD. Archive entries are never extracted.

`validate()` enforces version, basic provenance, allowed record/node fields, types,
positive numeric values, root identity and recursive tree shape before output.
Tests additionally compare dictionary values and coverage against original XML.

Statistics count all inspected SVG filenames, enriched/missing dictionary entries,
frequency entries, supplementary dictionary keys, alternative stroke counts,
unnamed groups, and unresolved named node occurrences in retained trees.
`unresolved_bases` aggregates the latter by lookup key; unnamed groups are counted
separately. KanjiVG-only glyphs do not extend the master character set. Unknown
meaning is represented by no lookup result, never guessed text.

Schema changes require updating this document, builder, validator, tests and future
runtime consumers, and incrementing `schema_version` when incompatible.

See [unresolved component audit](unresolved-components.md) for the reviewed lookup
gaps and [rendering policy](rendering-policy.md) for the presentation projection.
Presentation must not rewrite the stored raw tree.


## Sidecar provenance (master schema unchanged)

`generated/manifest.json` accompanies the bundled database; installed copies live
at `data/manifest.json`. Manifest version 1 records master schema 1, builder
compatibility 1, full database SHA-256, source identities, KANJIDIC2 XML snapshot,
optional retrieval date/HTTP validators and KanjiVG release tag. Unknown baseline
retrieval dates remain null. A retrieval date is not a dictionary version.
The development CLI writes this sidecar with deterministic null retrieval metadata.
See [database updates](../database-updates.md) for the validated immutable generation
pairs and atomic selection used by the desktop updater.
